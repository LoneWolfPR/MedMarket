**Design decision — prescription + order model (2026-07-07, applies Day 3+).** Agreed with user before starting the domain work:
- **Prescription:** `user_id`, uploaded doc (→ **MinIO**; store the object key on the record, not the blob), physician name, medication name (**free text**, normalized lowercase/trim at the adapter boundary to match how the mock catalogs compare — a typo just yields no search results), a **`Strength` value object** = numeric value + **unit enum** (mg/ml/mcg/g…; mg vs ml not interchangeable, no conversion), and **`quantity`** (dose count — lives on the prescription because it's part of the prescription the patient holds; **replaces** the originally-proposed `duration`, which is dropped; no dosage-frequency modeling). The prescription's med name + strength ARE the `PharmacyClient.Search` input.
- **Order:** stays lean — `prescription_id`, **order-vocabulary** `status` only (e.g. `placed`/`confirmed`/`shipped`/`delivered`/`canceled`), which **pharmacy**, the pharmacy's returned **order id** + **tracking id**, **price paid**, and **`quantity`** (copied from the prescription at order time — prescription is source of truth — so the order records what was actually bought). No shipping-status column, **no shipment entity** — shipping vocabulary stays behind the `ShippingClient` adapter + workflow.
- **Status split (Temporal):** order lifecycle is durable in Postgres (order vocabulary only); fine-grained shipping detail is **Temporal workflow state**, not a DB table. **Signal in / query out:** mock-shipping webhook → backend endpoint → **signal** the order workflow → workflow updates its in-memory shipping status and, via an **activity**, writes the coarse order-status transition to Postgres at thresholds (first shipping event → `shipped`, `delivered` → `delivered`); shipping's `picked_up`/`in_transit`/`out_for_delivery` **map into** the order enum, never stored raw (hexagonal boundary — order domain takes no dependency on shipping's vocabulary). A **new status API endpoint** does a Temporal **query** to read the live shipping detail (real-world use: customer-support tooling). Queries only work while the workflow is open (+ retention), so the endpoint **falls back to the Postgres order status** for completed/aged-out orders.

- **Mock-pharmacy-a gained a shipping address** (Claude): `POST /api/v1/order` now takes `shipping{name,street1,street2,city,state,zip}` and returns `400 {error:"invalid_shipping", missing:[...]}` alongside `404 unknown_sku`. **Validation runs before the SKU lookup**, so a request bad both ways gets the 400. A was built off-spec without it. B is unchanged — nested `recipient{name,line1,city,state,postalCode}`, required by its GraphQL schema. ⇒ the `PlaceOrder` port input **must carry a shipping address**; A maps it flat, B nests it. **B has no `line2`** but `shared.Address` has `Street2` — drop or fold into `line1` is the **user's call at step 4**.
- **Step 3 — order domain + persistence (built + tested).** `domain/order.Order` = `ID`/`PrescriptionID`/`OfferID`/`Status string`/`PharmacyOrderID`/`TrackingID`/`Qty int`/`PricePaid *shared.Money`. **No `PharmacyID`** — reachable through the offer, which owns which pharmacy quoted. `NewOrder` takes only rx/offer/qty and always starts at `StatusPlaced`: it takes **no** status param, because `mapToDomainOrder` builds a struct literal by convention, so reconstructing an advanced order already bypasses the constructor — a status param would remove a guarantee without adding a capability. Exported status constants feed `AcceptedStatuses`. Port = `Create`/`Update`/`GetByID` + `ErrOrderNotFound`. Migration `20260716200404_add_order`.
- **`PricePaid *shared.Money` — the domain's first pointer field.** nil = not captured. Required because `Money`'s zero is a legitimate $0.00 (full insurance), so zero cannot mean "unpaid" — unlike `Phone`/`Email`, which have a spare empty-string value. **The authorized amount is deliberately not stored:** it is derivable (offer price × qty), and only the *uncomputable* fact — what the processor actually captured — earns a column. The offer is a promise; the order is a fact, and the system that moved the money is the authority on how much moved. Mapping chain: `*int64` (Ent, nil=NULL) → deref → `int64` → `NewMoneyFromCents` → `shared.Money` → `ptr.To` → `*shared.Money`. The two pointers are unrelated — one is about a nullable column, the other about an unpaid order. `internal/ptr`'s `Deref`/`To` are the two ends; `MapToOAPIAddress` is the precedent. **This pointer cost three compile-clean runtime bugs in the first adapter pass** (nil deref on read, nil deref on update, and a `&value` that made every unpaid order read back as paid-$0.00) — the integration test now pins all three.
- **Status is validated by a DB CHECK, not the domain.** `NewOrder` no longer takes a status and the saga advances orders by assigning the exported field, so nothing in Go guards the column. `ent/schema/order.go` renders `status IN (...)` **from `order.AcceptedStatuses`** — one definition of the legal set, and `AcceptedStatuses` is load-bearing rather than dead. **First Ent schema to import the domain** (clean direction: adapters may depend on the domain, never the reverse). CHECK over `field.Enum` because the status list is expected to grow and `ALTER TYPE` is awkward. Same line as the FK decision: **constraints in the DB (declarative), behavior in the app (imperative)** — which is also why stored procedures were rejected for batching.
- **Deliberately deferred:** `tracking_id` index (the webhook that queries it lands at step 7); **status-transition enforcement** (the saga is the sole writer — and note the out-of-order-webhook case argues for *monotonic* guards, which would reject corrections too, so real corrections need an explicit path); the pharmacy's re-quoted total is **not stored** (the offer is the source of truth) — but **`PlaceOrder`'s port result must still carry it**, since the comparison happens where both numbers are known and the caller logs a `WarnContext` on divergence.

Sequenced before the HTTP work because `PlaceOrder`'s signature shapes both the saga and the order service. Then 5 → 6 → 7. **`main.go` order-repo wiring is half-done and won't compile** (`orderRep` declared and not used) — the repo has no consumer until the order service exists, the same wall the pharmacy adapters hit on Day 5; finish it alongside the service. ## Conventions

- All external dependencies accessed through port interfaces in ports/outbound/
- Adapters implement port interfaces, wired together in cmd/server/main.go
- Tests use testcontainers-go for integration tests needing Postgres
- golangci-lint must pass before committing
- Idiomatic Go is an explicit goal — the user is learning Go from a JS/TS/PHP/Java (OO) background. Favor the idiomatic Go construct (first-class functions/closures where a thing is essentially one behavior, e.g. middleware; small interfaces; struct+constructor only when a type holds dependencies *and* exposes multiple behaviors or satisfies an interface). Principle: reach for the smallest construct that fits, not "structs everywhere." When a choice diverges from OO-language habits, call it out and explain the Go reasoning rather than silently picking.
